LightRAG 2.0：分块策略全解析——四种方式怎么选？

发表于 2026-07-25 更新于 2026-08-20 分类于 LightRAG 源码解读 本文字数： 1.5k 阅读时长 ≈ 6 分钟
对比固定长度、递归、语义和结构化分块，说明 RAG 场景下如何根据文档与检索目标选择策略。

一、分块在解决什么问题

任何 RAG 系统要处理长文本，第一件事就是把它切成小块。不切，LLM 的 context window 装不下，向量检索也会因为语义稀释而失效。

但切割本身带来四个决策点：

  1. 块切多大？ 1200 tokens 够吗？3000 呢？
  2. 相邻块之间要不要重叠？重叠多少？
  3. 在哪儿下刀？ 走到第 N 个 token 就切，还是找一个自然边界再切？
  4. 一刀把一句话从中间劈开，影响检索吗？

第四个最难定。LightRAG 的四种策略，本质上就是对“在哪儿下刀”这个问题的四种不同回答。

二、四种策略对“在哪儿下刀”的回答

为了看清区别，考虑一段三段式文本：

第一部分：产品介绍，连续 2000 tokens，没有段落分隔符 第二部分：15 条新闻，每条有独立标题，各约 200 tokens 第三部分：技术说明书，5 个并列章节，段落之间用 \n\n 分隔

F — Fixed Token：数到第 N 个 token 就切，不关心内容

第 1 块：tokens 1–1200 第 2 块：tokens 1101–2300（重叠 100 tokens） 第 3 块：tokens 2201–3400 第 4 块：tokens 3301–4500 第 5 块：tokens 4401–5000

唯一能影响边界的是 split_by_character 参数——如果指定先用分隔符粗分，会在粗分结果上再做 token 级切割。否则就是在任意位置硬切，中间切到哪个词就是哪个词。

结果：5 块，可能每块中间都切断了句子或概念。但块数可预测，输入输出稳定。

优点：最简单、最稳定、最快，没有外部依赖。
缺点：语义完整性最差，概念可能被从中间劈开。

R — Recursive Character：按分隔符层级，优先找自然边界

`
先试 \n\n（段落）

第一部分（2000 tokens，无 \n\n）
→ 降到 \n，也没有
→ 降到句号/分号
→ 降到逗号
→ 降到空格甚至字符级才切得动

第二部分（每条新闻 200 tokens）
\n\n 级别就能解决——标题之间有空行

第三部分（5 个章节）
每个章节被 \n\n 分隔，刚好一块一个章节
`

结果：块数不确定，但边界比 F 自然得多，不会在词中间硬切。

优点：自然边界保持得最好，适合自然语言文本。
缺点：块大小不可控——如果一段 3000 tokens 且没有段落/句子边界，整段就是一块。

V — Semantic Vector：在话题切换的地方下刀

先切句子，对每句做 embedding，算相邻句子的余弦距离。距离突变的点就是“话题切换了”，就在那里切开。

余弦距离曲线： \u2502 \u2502 \u2571\u2572 \u2571\u2572 \u2571\u2572 \u2502\u2571 \u2572 \u2571 \u2572 \u2572\u2571 \u2572\u2571\u2572 \u2571\u2572\u2571 \u2572 \u2502 \u2572\u2571 \u2572\u2571 \u2572\u2571 \u2572\u2571 \u2502 \u2572\u2571 \u2517\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501\u2501 \u2191 话题A \u2191 话题B \u2191 话题C \u2191 话题D 切 切 切 切

第一部分：2000 tokens 的产品介绍，如果内部没有话题切换，整段不会切。
第二部分：15 条新闻，如果每条新闻算一个话题，会在新闻之间切开。
第三部分：5 个章节，如果每个章节是不同话题，也会在章节边界切开。

阈值算法有四种可选：percentile（默认）、standard_deviation、interquartile、gradient。控制“多大的距离突变才算话题切换”。

优点：边界最“语义化”——在实际话题切换处下刀。
缺点：需要 embedding 模型参与分块，速度慢；块大小完全不可控。

P — Paragraph Semantic（LightRAG 独有）：利用已有标题层级来组织块

前三者都是“从头切割”——文本进来，自行决定从哪儿切。P 策略不同：它依赖文档解析器产出的 .blocks.jsonl 副产品，在此之上做精细调整，而不是无中生有地找边界。

`
原始文档：
h1: 产品介绍
h2: 产品规格
h2: 性能参数
h3: CPU 性能
h3: GPU 性能
h2: 价格信息

五阶段 Pipeline：

  1. HeadingBlocks → 标题级初分，每个 block 带标题层级
  2. TableRowSplit → 超大表格按行拆分，非首块重新注入表头
  3. AnchorSplit → 短文段（<= 100 字符）作为锚点重平衡块
  4. HeadingGlue → 无正文标题粘到下一个子标题块前面
  5. LevelMerge → 底向上合并太小块，先同级再上级
    `

优点：保持标题层级结构，后续实体提取和查询都能拿到“标题面包屑”。
缺点：依赖结构化解析器，纯文本或无标题的文档无法使用。

三、四种策略的对比

策略 “在哪儿下刀”的回答 块大小 语义完整性 额外依赖
F 走到第 N 个 token 就切 可控（固定窗口） 低 无
R 在分隔符的递归边界上切 不可控 中高 langchain-text-splitters
V 在语义向量距离突变处切 不可控 高 langchain-experimental + embedding
P 在文档已有的标题边界上切 半可控 高（保留层级） 解析器的 blocks.jsonl

R、V、P 策略的输出块如果仍然超出 token 上限，会在 embedding 前由 enforce_chunk_token_limit_before_embedding 做一次硬切作为兜底。

四、实际怎么选

F：通用场景，API Server 默认，速度快且稳定。如果不确定用什么，用 F 不会错。

R：文档段落结构清晰但用的是纯文本格式（markdown、代码），希望保持自然段落边界。

V：需要按话题切换来分块的长文档（报告、论文），对边界质量要求高，能接受速度慢。

P：Word 或 PDF 这类带标题层的文档，希望保持标题结构以便查询时精确定位到章节。

五、分块后的去向

不管哪种策略走完，产出物都汇入同一条管道：

`
分块完成后
→ 每块做 embedding → 存入 chunks_vdb（向量库）
→ 每块的原始内容 → 存入 text_chunks（KV 存储）
→ 分块继续进入实体提取管线（LLM 抽取实体和关系）
