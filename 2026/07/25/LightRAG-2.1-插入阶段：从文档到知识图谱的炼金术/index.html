LightRAG 2.1：插入阶段——从文档到知识图谱的"炼金术"

发表于 2026-07-25 更新于 2026-08-20 分类于 LightRAG 源码解读 本文字数： 1.7k 阅读时长 ≈ 6 分钟
沿着 LightRAG 插入流水线，拆解文档分块、实体关系抽取、图存储和向量索引的协作方式。

一、回顾：LightRAG 的两个阶段

前面 1.x 系列文章详细拆解了 LightRAG 的查询路径：关键词提取 → 批嵌入 → 向量检索 → Graph Store 编排 → Token 裁剪 → Context 组装 → LLM 调用。

但查询的前提是数据已经在库里了。数据是怎么进去的？这就是本文要讲的插入阶段。

二、插入流程总览

三、第一步：分块（Chunking）

在进入实体提取之前，LightRAG 先做了所有 RAG 系统都会做的一件事——把长文本切成小块。这一步好坏直接影响检索质量：块太大，细节被稀释；块太小，语义不完整。

LightRAG 提供了四种分块策略：

F - Fixed Token（默认）

最简单、最稳定的策略。直接按 token 数切固定窗口：

如果指定了 split_by_character，会先按分隔符粗分，再对超出 token 上限的段做二次切割。

ainsert 方法只支持这种策略，因为它走得是旧的 6 参数签名。API Server 支持全部四种。

R - Recursive Character

基于 LangChain 的 RecursiveCharacterTextSplitter。按分隔符的语义层级递归切割：

优先保留更自然的语义边界，适合段落结构清晰的文本。

V - Semantic Vector

基于 LangChain 的 SemanticChunker。先用 embedding 把相邻句子映射到向量空间，然后在向量距离突变的地方切开：

边界最”语义化”，但速度较慢，且需要 embedding 模型。如果没配 embedding，它会自动回退到 R 策略。

P - Paragraph Semantic（LightRAG 独有）

这是 LightRAG 自己的策略，也是四种中最复杂的一个。它依赖 parser 产生的 .blocks.jsonl 副产品文件（heading-based blocks），在已有标题层级的基础上做精细的段落合并与拆分：

最适合 Word、PDF 这类有天然标题结构的文档。默认的 chunk_token_size 设得比 F 策略大一些（环境变量 CHUNK_P_SIZE，默认 2000），因为标题对齐的块需要更多空间来保持语义完整。

如何选择策略？

策略 场景 成本
F - Fixed Token 通用、稳定、无额外依赖 最低
R - Recursive Character 自然语言段落结构清晰 低
V - Semantic Vector 需要语义边界精确的场景 高（需 embedding）
P - Paragraph Semantic Word/PDF 等带标题结构文档 中（需 blocks.jsonl）

三、核心：LLM 实体-关系提取

这一步不是简单提取关键词，而是给 LLM 发一个精心设计的 prompt，让它输出结构化的实体和关系。

给 LLM 的 system prompt 要点

在 lightrag.prompt 中定义了一个很详细的 system prompt，核心指令大致如下：

实体提取要求：

  • 对每个实体，提取 entity_name、entity_type、entity_description
  • entity_type 使用预定义的类型（如 Organization、Person、Product、Technology 等）
  • 描述要基于文本本身，不能自己编

关系提取要求：

  • 识别实体之间直接、明确的关系
  • 对每个关系，提取 source_entity、target_entity、relationship_keywords、relationship_description
  • 如果一个句子涉及多个实体，拆成多个二元关系

举个例子，对于文本：

“Apple 发布了新款 MacBook Pro，搭载 M4 芯片。”

Gleaning（二次提取）

第一次提取之后，LightRAG 还有一个可选的 gleaning 步骤（默认开启）：把第一次提取的结果作为对话历史，再问一次 LLM “还有没有遗漏的实体和关系？”。这能捕获第一次提取时漏掉的内容，但会增加一次 LLM 调用。如果输入已经很长了，gleaning 会被自动跳过以免超 token 限制。

四、提取结果流向何方

提取完成后，数据分三条路进入不同的存储：

1. 实体（Entities）

  • 实体的 name、type、description 存入 full_entities（KV 存储）
  • 实体的 description 做向量化，存入 entities_vdb（向量存储）
  • 实体在 chunk_entity_relation_graph（图存储）中作为节点存在

2. 关系（Relationships）

  • 关系的 source、target、description 存入 full_relations（KV 存储）
  • 关系的 description 做向量化，存入 relationships_vdb（向量存储）
  • 关系在图存储中作为边存在

3. 文本块（Chunks）

  • 分块后的文本内容、token 数、来源文档 ID 存入 text_chunks（KV 存储）
  • 文本块做向量化，存入 chunks_vdb（向量存储）

为什么需要三个向量库？

向量库 存什么 被什么模式使用
chunks_vdb 文本块的语义向量 naive、mix
entities_vdb 实体描述的语义向量 local、hybrid、mix
relationships_vdb 关系描述的语义向量 global、hybrid、mix

查询时，不同模式查不同的向量库，然后用不同的路径来组合结果。

五、这和标准 RAG 的关键区别

标准 RAG 的插入阶段只有一条线：

LightRAG 在这个基础上多加了一条线，用 LLM 做了一次”翻译”——把非结构化的自然语言变成结构化的实体-关系图。代价是在插入阶段多花了一次（或两次）LLM 调用。收益是查询阶段能做关系推理，而不仅仅是文本相似度匹配。

这就是”知识图谱 + RAG”的核心 trade-off：用插入阶段的 LLM 成本，换查询阶段的推理能力。
