入门 Coding Agent（一）：从 Prompt 到循环——Agent 的核心工作原理

发表于 2026-07-25 更新于 2026-08-20 分类于 Coding Agent 原理 本文字数： 1.1k 阅读时长 ≈ 4 分钟
从推理、执行到观察，拆解 Coding Agent 如何通过循环把一次自然语言任务变成连续的行动。

一、你每天都在用，但未必了解它的原理

如果你用过 Cursor、Copilot、Devin，或者任何能”自主编程”的 AI 工具，你已经在和 Coding Agent 打交道了。但大多数人对它的理解停留在”能写代码的 AI”这个层面。

这篇文章会用最直白的方式，拆解一个 Coding Agent 到底是怎么工作的。

我们从一个问题开始：Coding Agent 和普通 LLM 聊天的本质区别是什么？

和 LLM 聊天时，你问一句它答一句，对话是线性的。而 Coding Agent 做的事情不同——你给它一个任务后，它自己决定下一步做什么，拿到结果后再决定要不要继续。

这个”自己决定”的能力，就是 Agent 和普通聊天的分水岭。

二、Agent 的核心循环：推理 → 执行 → 观察

一个 Agent 的整个生命周期，就是在一个循环里打转：

这个循环的每一步都只做一件事：

  1. 推理：把到目前为止的完整对话历史发给 LLM，问它”下一步做什么”
  2. 执行：LLM 返回的不是文字答案，而是一个或多个动作（action），比如”帮我跑一下 ls src/“。Agent 把这些动作交给执行环境去跑
  3. 观察：执行环境返回结果（命令的输出、错误码等），Agent 把这个结果追加到对话历史里
  4. 回到第 1 步：LLM 现在看到了执行结果，再做下一步决策

这个循环会一直持续，直到 LLM 觉得任务完成了。

三、对话历史就是 Agent 的”记忆”

Agent 不维护什么复杂的状态管理。它唯一的”记忆”就是一条不断增长的消息列表。格式大概是这样的：

每一次循环，消息列表都在增长。LLM 每次都看到全部历史，所以它能感知到上下文的变化——上一轮的命令有没有报错、测试有没有通过、环境发生了什么变化。

这个设计的巧妙之处在于：Agent 不需要专门的状态管理，消息列表本身就是状态。

四、普通聊天 vs Agent 循环

普通 LLM 聊天 Coding Agent
交互方式 用户问一句，LLM 答一句 Agent 自行决定下一步
工具调用 无，只能生成文字 可以执行 shell 命令、修改文件、跑测试
反馈机制 用户的下一个问题 执行环境的真实返回结果
终止条件 用户停止提问 LLM 主动提交，或被硬边界截停
状态管理 用户维护上下文 消息列表自动累积

五、一个关键问题：谁来喊停？

Agent 循环是 while True，那它怎么知道什么时候停下来？

直觉上你会觉得”LLM 自己判断任务完成了”。这个判断是对的——正常退出确实依赖 LLM。但它不是”说”自己完成了，而是通过执行一个特殊动作来提交：

执行环境（Environment）检测到输出以 COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT 开头，就触发退出信号。Agent 捕获到信号后退出循环。

为什么绕这么一圈？因为LLM 是不可靠的。它可能说着说着就编造了不存在的东西，可能在一个死胡同里绕圈子，也可能”觉得”自己做完了但实际是错的。强制它通过一个结构化的动作来提交，比让它”说”我完成了更可靠。

但依赖 LLM 来”主动提交”只是软退出。还有硬边界——这个话题我们放到第三篇详细讲。
