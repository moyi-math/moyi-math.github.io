LightRAG 2.2：LLM 缓存——同一个问题别花两次钱

发表于 2026-07-25 更新于 2026-08-20 分类于 LightRAG 源码解读 本文字数： 853 阅读时长 ≈ 3 分钟
解析 LightRAG 的查询、提取和关键词缓存，说明缓存键设计如何降低重复 LLM 调用的成本与延迟。

一、为什么要缓存 LLM 调用？

LLM 调用有两大成本：

  • 金钱：每次调 GPT-4 或类似模型都要按 token 付费
  • 时间：一次 LLM 调用通常需要几百毫秒到几秒

在 RAG 系统里，同一个问题被不同用户反复问，或者同一个文本块被反复处理，是常见的场景。如果没有缓存，每一次都是真金白银加等待时间。

LightRAG 实现了两层缓存来应对这个问题。

二、两层缓存

第一层：查询缓存（Query Cache）

缓存 key 怎么算的？

compute_args_hash 函数把所有影响 LLM 回答的参数全算进一个 MD5：

  • mode（local / global / hybrid / mix / naive）
  • query 文本本身
  • response_type
  • top_k、chunk_top_k
  • max_entity_tokens、max_relation_tokens、max_total_tokens
  • enable_rerank 开关
  • LLM 模型标识

第二层：提取缓存（Extraction Cache）

插入阶段调 LLM 提取实体和关系时，也会查缓存。场景是：如果同一个文档块被重新处理（比如某次处理失败后重试），已经提取过的实体不需要再花钱调 LLM。

提取缓存的 key 由 prompt、system_prompt、history_messages 和 response_format 的 hash 组成。

三、两个缓存独立开关

可以单独关掉某个缓存。比如开发调试时可能关掉查询缓存以获取最新回答，但保留提取缓存避免重复处理。

四、缓存存在哪里？

llm_response_cache 是一个 KV 存储实例，和 LightRAG 的其他存储一样支持插拔：

  • 默认：JSON 文件存储，存在 working_dir 下（文件名为类似 kv_store_llm_response_cache.json）
  • 也可以：换成 Redis、PostgreSQL、MongoDB 等

六、一个常见的陷阱

如果你在项目中切换了 embedding 模型（比如从 text-embedding-3-small 换到 text-embedding-3-large），缓存 key 不包含 embedding 模型信息。因此：

  1. 缓存的 LLM 回答仍然是基于旧 embedding 检索到的图谱内容生成的
  2. 但实际使用的图谱向量是新的 embedding 空间，检索结果可能不同

这就是为什么在切换 embedding 模型时，官方建议清空数据目录，但可以保留 LLM 缓存文件——LLM 回答本身不受 embedding 变化影响，下次查同样的 query 还能命中旧缓存。不过需要理解这存在一定的语义偏差风险。
