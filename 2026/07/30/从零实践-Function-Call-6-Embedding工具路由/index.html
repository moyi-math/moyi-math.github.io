从零实践 Function Call（六）：当工具有几十个——用 Embedding 做工具路由

发表于 2026-07-30 更新于 2026-08-20 分类于 从零实践 Function Call 本文字数： 1.2k 阅读时长 ≈ 5 分钟
面对大量工具时，用 Embedding 做语义路由，先筛选候选工具再交给 LLM 决策以降低上下文成本。

一、问题：09 只有 4 个工具，但真实系统有几十个

回顾 09_react-agent 的工具集：

全部传给 LLM 没问题。但如果系统涨到了 80 个工具呢？

带来的问题：

  1. 上下文成本：大量 token 被工具定义占用，留给对话的 token 变少
  2. 选错概率：工具越多，LLM 选到相似但错误工具的概率越高
  3. 延迟：工具定义过多可能拉长首 token 时间

二、解法：RAG 思想用在工具选择上

核心思想：Tool routing = RAG for tools。示范短语就是文档，用户消息就是查询，余弦相似度就是检索。

三、核心代码就两个函数

评分函数

一个工具可以有多个示范短语。评分取最大值——只要有一个短语匹配上，工具就应该被考虑。

选择函数

两步分开，每步可独立测试。这是好的工程设计的标志。

四、什么是 Pinned（钉子工具）

有些工具不参与相似度竞争，永远在结果集里：

pinned 的工具不消耗 k 的配额。k=1 + pinned=1 → LLM 实际看到 2 个工具，但只用了 1 个检索槽位。

五、6 个演示场景

场景 用户说 k 选中工具 结果
VPN 故障 “Cisco 客户端连不上” 1 checkVPNStatus ✓ 精准命中
账户锁定 “密码输错太多次” 1 getUserAccount ✓ 精准命中
电脑崩溃 “蓝屏了，查日志并跑硬件诊断” 2 getSystemLogs + runDiagnostic ✓ 双意图命中
磁盘满 + 版本查询 “装不上更新，顺便问 Office 版本” 2 checkDiskSpace + getInstalledSoftware ✓ 双意图命中
VPN + 锁定（k=1） “VPN 认证失败，密码也不对了” 1 只有 checkVPNStatus ✗ 漏了账户工具
同上 + pinned 同样的话 1+pinned checkVPNStatus + getUserAccount ✓ 全命中

第五个场景是特意设计的召回失败演示——用户说了两件事（VPN + 账户），但 k=1 只取到相似度更高的 VPN 工具。

第六个场景展示 pinned 的解法：getUserAccount 被钉入 always-include，不占 k 的配额。

六、为什么没有 Cross-encoder 重排序？

你可能会问：只用 bi-encoder 够吗？为什么不需要 cross-encoder 做第二阶段重排？

对比两种 Embedding 模型：

当前代码只有 12 个工具 × 3 个示范短语 = 36 次相似度计算，bi-encoder 几毫秒跑完。cross-encoder 虽然更精确，但要跑 36 次推理，慢 10-100 倍。对于这个规模，精度提升不值得多花的时间。

真需要 rerank 的场景是几百个工具：

这就是 RAG 里经典的两阶段检索：先用轻量模型宽召回，再用重量模型做精排。

七、三个关键设计决策

  1. 用 max 不是 mean：一个工具多个示范短语，取最高分而不是平均分——只要有一个短语强烈匹配，工具就应该被考虑。

  2. k 的权衡：k 太小 → 漏工具（recall 失败）；k 太大 → 噪声重新进入 prompt。需要实测找到平衡点。

  3. 示范短语 ≠ 用户问题的拷贝：好的示范短语是多样化的 paraphrase，不是从真实对话里复制粘贴。否则路由看起来”准”，但换个说法就露馅。

八、核心洞见

这个例子没有改变 function call 的机制——它改变的是决定把哪些工具传给 function call。

就像 RAG 让 LLM 不需要记住所有知识一样，工具路由让 LLM 不需要看到所有工具。
