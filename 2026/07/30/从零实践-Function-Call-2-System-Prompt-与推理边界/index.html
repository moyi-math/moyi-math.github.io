从零实践 Function Call（二）：System Prompt 的艺术与纯推理的边界

通过 System Prompt 和工具描述，拆解 LLM 的纯推理边界，以及它何时应该把任务交给工具执行。

一、引言

上一篇我们用 60 行代码展示了 Function Call 的完整机制。但你可能会想：LLM 怎么知道什么时候该调用工具？怎么知道该传什么参数？怎么保证它不滥用工具？

答案都在 System Prompt 里。

System Prompt 是 Agent 的”操作手册”。同一个模型，配上不同的 System Prompt，可以是翻译官、数学老师、客服、代码助手——模型没变，行为变了。

五、纯 LLM 推理的边界

有了好的 System Prompt，LLM 能解决复杂问题了吗？不一定。

试试这个题：

这个题目需要：

  1. 数清家庭关系中的每一个人
  2. 区分成人和小孩
  3. 排除不吃碳水的人
  4. 按人头算土豆需求量
  5. 换算成磅
  6. 再换算成袋数（向上取整）

纯 LLM “心算”做这种题，经常出错。 原因有三：

问题 1：计算不可靠

LLM 本质上是语言模型，不是计算器。它”学过”数学，但每一步都是概率性的。三位数以上的运算，1.7B 模型的错误率明显上升。

问题 2：上下文窗口饱和

复杂的推理链会消耗大量 token。家庭聚餐这道题，光描述就有几百个 token，推理过程更容易撑爆上下文窗口。

问题 3：无验证机制

LLM 算出一个数就是最终答案。它没法回溯验证，没法”重算一遍”，也没法说”这一步我不确定，我用计算器确认一下”。

六、工具 = 给 LLM 配一个”计算器”

这些问题的解决方案从来不是”换更大的模型”——而是给 LLM 配工具。

对比两种方式：

每一步的计算都由工具完成，LLM 只负责决策——“下一步该算什么”，而不是”结果是多少”。

这就是 04_think 教给我们的核心教训：

LLM 应该做它擅长的（推理、规划），把不擅长的（计算、记忆、实时信息）交给工具。

七、从”身份设定”到”协议约束”的演进

一个关键的转折点是：你不再是在”教育”一个助手，而是在”编程”一个系统。 System Prompt 从”身份卡片”变成了”执行协议”。
