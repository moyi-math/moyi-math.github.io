Hello算法 学习笔记 · 6.2 哈希冲突：链式地址与开放寻址

发表于 2026-07-29 分类于 Hello算法学习笔记 本文字数： 2.4k 阅读时长 ≈ 9 分钟
哈希冲突无法避免——不同的 key 可能算出相同的索引。链式地址让每个桶变成链表，冲突了就往后挂；开放寻址冲突了就往后找空位。本文从冲突的产生到工业级解决方案，逐层拆解。

章节定位: 上节学了哈希表的核心机制——哈希函数把 key 映射成数组索引，实现 O(1) 查找。但哈希函数做不到完美：两个不同的 key 可能算出的同一个索引，这就是哈希冲突。本节讲两种工业级解决方案——链式地址和开放寻址，以及负载因子和动态扩容。

摘要(Abstract)

TL;DR: 哈希冲突是两个不同的 key 算出了相同的数组索引。它无法完全避免——因为桶的数量总是有限的，而可能的 key 数量是无限的。两种主流解法：链式地址把每个桶变成一个链表（或数组），冲突的元素挂在同一个桶里；开放寻址冲突了就往后面的空位放。两种方案都需要关注负载因子（已占用的比例），超过阈值就必须扩容（翻倍重建），否则性能会急剧恶化。

  • 链式地址: 每个桶变成一个链表，冲突吗？挂后面
  • 链式地址的扩容: 负载因子超阈值时翻倍重建

适合读者: 想理解哈希表”环环相扣的设计”的学习者；想知道 Python dict 为什么这么快、怎么处理冲突的开发者。

一、哈希冲突的产生

上节的 ArrayHashMap 有一个致命问题：

为什么哈希冲突无法避免？

  • 桶的数量是有限的（比如 100 个）
  • key 的可能值是无限的（学号可以是任意整数）
  • 根据鸽巢原理，把无限个 key 放进有限个桶，必然有多个 key 落在同一个桶里

好的哈希函数只能减少冲突，无法消除冲突。

二、负载因子——哈希表的”拥挤程度”

size capacity load_factor 状态
3 10 0.3 空闲，冲突概率低
6 10 0.6 适中
8 10 0.8 拥挤了，需要扩容

负载因子越大，冲突概率越高，性能越差。 工业级哈希表会在负载因子超过阈值时自动扩容（通常是 0.75 或 2/3）。

三、方案一：链式地址（Separate Chaining）

每个桶不再存单个值，而是存一个链表（或数组、红黑树）。冲突的元素都挂在同一个桶里。

追踪 put(12836, "小哈") 和 put(10036, "小明")：

链式地址的查找

最好的情况：桶里只有一个元素 → O(1)
最坏的情况：所有 key 都在同一个桶里 → **O(n)**（退化成链表）

动态扩容

扩容为什么必须”重新插入”而不是直接拷贝？

因为 hash_func(key) = key % capacity——容量变了，同一个 key 的索引也会变！

所以扩容后每个 key 都要重新算索引、重新放——这就是 O(n) 的操作。好在扩容不频繁（翻倍后很久才会再触发），均摊下来 O(1)。

四、方案二：开放寻址—线性探测（Open Addressing）

链式地址用额外空间（链表）解决冲突，开放寻址不用额外空间——冲突了就往后面的空位放。

追踪 put(12836) → put(10036) → put(36)（容量=4）：

线性探测的折返： 当 index 走到数组末尾 capacity-1 时，通过 (index + 1) % capacity 回到数组开头继续找。这和队列的循环数组是同一个思路。

开放寻址的删除——墓碑（TOMBSTONE）

开放寻址的删除不能直接置空：

解决方案：用”墓碑”标记删除位置，不能直接置空。

墓碑的作用： 探测时遇到墓碑不停止，继续往后走。这样就能跨过已删除的位置，找到后面的元素。但墓碑太多会降低性能——所以墓碑多了也需要触发扩容清理。

五、两种方案对比

维度 链式地址 开放寻址
额外空间 需要（链表节点） 不需要
删除 直接移除节点 需墓碑标记，复杂
缓存友好 ❌ 链表节点散落，不友好 ✅ 连续数组，友好
负载因子阈值 ~1（链表可以很长） < 1（满了就真满了）
最坏情况 O(n)（全挂一个桶） O(n)（探测链过长）
实现复杂度 简单 较复杂（墓碑处理）
典型使用 Java HashMap Python dict（探测 + 扩容）

note

Python dict 实际用哪种？ Python 的 dict (CPython 3.6+) 用的是开放寻址 + 伪随机探测，结合了紧凑存储和快速查找的优势。早期版本还有专门的优化——如果你只遍历 dict 而不修改，插入顺序会被保留（这是 3.7 起的语言特性）。

七、面试高频题

Q1: 负载因子是什么？为什么要设置负载因子阈值？

负载因子 = 元素数量 / 桶的总数，衡量哈希表的”拥挤程度”。阈值的作用是在哈希表变得太拥挤之前触发扩容。如果负载因子太高，冲突概率剧增，查找性能从 O(1) 退化成 O(n)。不同语言设置的阈值不同：Java 的 HashMap 是 0.75，Python 的 dict 大约在 2/3 左右。

Q2: 链式地址和开放寻址各自适用于什么场景？

链式地址适合对写入性能要求高、删除频繁的场景（直接删节点即可），也适合存储大型对象的场景（链表节点本身存引用，不占太多额外空间）。开放寻址适合数据量可预估、追求缓存命中率的场景——连续数组的缓存友好性在高性能场景下是巨大优势。

Q3: 为什么开放寻址的删除不能直接置空，要用墓碑？

因为开放寻址的查找依赖探测链。如果某个位置被置空，探测链就会在这里断裂——后面的元素就再也找不到了。墓碑标记告诉探测逻辑”这里曾经有元素，继续走”，维持了探测链的完整性。但墓碑多了也会降低性能（探测跳过墓碑需要额外步骤），所以需要定期清理或触发扩容。

下一节预告: 哈希表之后，我们的视野从线性结构进入树形结构——树（Tree）。树是一对多的层次结构，最常见的是二叉树。树的遍历（前序、中序、后序、层序）和二叉搜索树（BST）是核心内容。
