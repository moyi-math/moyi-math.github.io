MCP 入门（一）：为什么 AI 需要 USB-C——从痛点理解 Model Context Protocol

发表于 2026-07-31 分类于 MCP 学习笔记 本文字数： 1k 阅读时长 ≈ 4 分钟
当每个 AI 模型对接每个工具都要写一遍胶水代码时，问题就来了。本文从实际开发者的痛点出发，一步步推导出 MCP 为什么存在、解决什么问题、以及它的核心架构。

一、一个后端开发者的烦恼

假设你写了一个天气查询工具。它很简单：输入城市名，返回当前温度。

你想让 AI 能用上它。于是你：

  1. 为 OpenAI 写了一个 function calling 的 JSON Schema
  2. 为 Claude 写了一个 tool use 格式的描述
  3. 为本地跑的其他 AI Agent 又写了一套接口

三个 AI，三个工具描述格式，三份胶水代码。工具本身只有一个。

如果你有十个工具呢？对接五个 AI 平台呢？50 份胶水代码。

这就是 MCP 要解决的问题。

二、问题本质：AI 世界的充电器混乱

在没有 USB-C 之前，每个设备都有自己的充电线——手机一根、相机一根、耳机一根。出门带三根线是常态。

AI 工具集成的现状就是如此。

每个 AI 模型供应商定义了各自的”充电口”：

AI 平台 工具调用接口 格式
OpenAI Function Calling 自定义 JSON Schema
Anthropic Claude Tool Use 自定义格式
Google Gemini Function Declaration 自定义格式
开源模型 各不相同 各不相同

写一个函数给 OpenAI 用，不能直接拿给 Claude 用。接口格式不一样，接收的请求体不一样，返回的响应格式也不一样。

每个工具配每个模型都重写一遍——这就是碎片化的代价。

三、MCP 的答案：一个统一的标准

Model Context Protocol（MCP） 就是 AI 世界的 USB-C。它定义了一套开放、标准化的接口，让 AI 模型可以无缝地与外部工具、API 和数据源交互。

它的核心承诺是：

工具写一次，所有支持 MCP 的 AI 都能用。

你不需要关心对方用的是 OpenAI 还是 Claude——只要它支持 MCP，就能自动发现并调用你的工具。

这之所以可能，是因为 MCP 协议规定了：

  • 工具该长什么样（元数据格式）
  • 怎么被发现（自动列举）
  • 怎么被调用（请求/响应协议）
  • 用什么传数据（传输层）

四、MCP 的三层架构

MCP 采用经典的 客户端-服务器模型，由三个角色组成：

1. MCP Host（宿主）

运行 AI 模型的应用程序。比如：

  • Claude Desktop
  • VS Code（通过 MCP 插件）
  • 自定义 AI Agent 应用

Host 负责管理用户界面、协调 AI 模型、维护多路服务器连接。

2. MCP Client（客户端）

Host 内部的一对一连接器。每个 MCP Server 对应一个 Client。Client 负责：

  • 用 JSON-RPC 2.0 协议与 Server 通信
  • 协商协议版本和功能
  • 处理工具调用请求

一个 Host 可以有多个 Client，连接多个 Server。

3. MCP Server（服务器）

你写的工具程序。每个 Server 暴露一组特定能力。可以跑在你的电脑上（本地），也可以部署在云端（远程）。

  1. 把你的 Python 函数签名翻译成 AI 可读的 JSON Schema
  2. 注册到内置的 tools/list 和 resources/list 接口

作为开发者，你只关心写函数。暴露出去的事，MCP 帮你做了。

六、小结

概念 一句话
MCP 是什么 AI 工具的统一接口协议
为什么需要 避免每个工具配每个模型都重写代码
类比 USB-C 之于充电器，MCP 之于 AI 工具
核心架构 Host → Client ↔ Server
