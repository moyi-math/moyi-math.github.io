二、为什么要分层测试

Server 跑起来只是开始。当你写了 20 个工具函数，每次测试都要启动进程、连客户端、调工具，开发效率会很低。MCP 提供了三种测试手段，本质是三个层级：

层级 传输方式 适合场景
第一层：单元测试 内存流（不启动进程） CI 自动化，快速回归
第二层：MCP Inspector STDIO（启动本地进程） 开发时人工调试
第三层：HTTP 手动测试 HTTP（远程服务） 部署后冒烟测试

三层的本质是同一套 MCP 逻辑，换不同的传输方式。

三、第一层：单元测试——内存会话机制

核心问题：怎么做到”不启动进程也能通信”？

回顾 MCP 的分层架构：

正常运行时，Client 和 Server 通过 STDIO 通信——本质是操作系统的管道，数据从一个进程流到另一个进程。

单元测试的巧妙之处在于：传输层是可替换的。

MCP SDK 内置了一个”内存传输层”，它不经过操作系统管道，而是在同一个进程里造一对互相连接的虚拟管道，让 Client 和 Server 直接通过内存对象收发消息：

为什么这样可行？

因为 MCP 协议本身就是 JSON-RPC 消息——Client 发的是结构化请求，Server 收到后解析、路由、返回。传输层只是负责把这串数据从 A 挪到 B：

  • 用 STDIO：数据通过管道挪
  • 用 HTTP：数据通过网络挪
  • 用内存流：数据通过 Python 协程/对象直接挪

挪的方式不同，但 Server 收到的请求一模一样。所以测试结果和真实运行是一致的。

SDK 的 create_connected_server_and_client_session 辅助函数替你完成四件事：

  1. 创建 Server 实例（不启动进程）
  2. 创建一对互连的内存流（扮演管道）
  3. 创建 Client 会话，接到内存流的一端
  4. 初始化握手（等价于真实连接时的 initialize）

四、第二层：MCP Inspector——它就是现成的 MCP Client

MCP Inspector 是官方提供的可视化调试工具，本质是一个现成的 MCP Client + 网页界面。

内部机制

你运行 mcp dev server.py 时，Inspector 会像你自己写的客户端一样：

  1. 连接：把你的 Server 作为子进程启动，通过 STDIO 连上去
  2. 发现能力：自动调用 tools/list、resources/list、prompts/list，把结果显示在网页上
  3. 测试工具：你在网页上填参数、点调用，Inspector 包装成 tools/call 请求发给 Server，拿到结果后渲染在页面上

Inspector 没有魔法。它做的事情和你手写的 client 一模一样——连上 Server、发 JSON-RPC 请求、收结果。区别只是界面：

手写 client MCP Inspector
界面 终端打印 网页可视化
谁写的 自己 官方预制
自动化 可以脚本化 人工交互为主

一句话：Inspector 就是别人写好的 MCP Client，加了一个 UI。

六、三层测试的本质

三种测试手段，对应 MCP 协议的一个核心设计：数据层与传输层分离。

层级 传输方式 适合场景
单元测试 内存流（不启动进程） CI 自动化，快速回归
MCP Inspector STDIO（启动本地进程） 开发时人工调试
HTTP 手动测试 HTTP（远程服务） 部署后冒烟测试

选择逻辑很简单：开发时用 Inspector 看效果，CI 用单元测试守回归，上线后用 HTTP 冒烟。
