入门 Coding Agent（五）：当对话撑满时——自动压缩机制与上下文管理

发表于 2026-07-29 更新于 2026-08-20 分类于 Coding Agent 原理 本文字数： 1.9k 阅读时长 ≈ 7 分钟
从上下文窗口耗尽的问题出发，说明 Coding Agent 如何压缩历史、保留任务状态并继续执行。

本篇基于对 Codex Desktop Runtime 的实际行为观察编写。所有机制来自对系统日志、数据库结构、以及 Agent 系统提示的交叉验证。

一、一个被忽略的问题：上下文不是无限的

前三篇我们构建了一个能在循环中自主工作的 Agent（核心循环），给它配了安全边界（保险丝设计），又通过 Goal 系统让它能跨 session 持续工作（跨会话持久化）。

但这里有一个更基础的问题一直没有被正面回答：每一次对话里，上下文是有限的。

不管是 Claude 的 200K、GPT-4o 的 128K，还是如今更主流的新模型——Claude 4 Sonnet 已达到 1M token、GPT-5 系列也迈入了 1M token 级别——上下文窗口都有上限。当 Agent 在一个长对话里不断调用工具、看结果、再调用工具，消息列表持续膨胀，最终一定会撑满窗口。

撑满之后会发生什么？

  • 丢弃最早的消息？那 Agent 会失忆，变成”盲人”
  • 直接报错？那对话终结，任务中断
  • 无限扩容？不现实，模型有硬限制

这个问题必须在 Runtime 层面解决。

二、两种方案：丢掉 vs 压缩

粗暴的方案是丢弃最早的消息——把最旧的那批对话删掉，腾出空间。ChatGPT 的网页版就用了这个策略：当上下文接近上限时，静默删除最早的几条消息。

这个方案的代价很直接：信息丢失。 如果最早的消息里包含了任务的初始需求、用户的关键约束、或者 Agent 已经完成的分析结论，丢掉了 Agent 就”忘了”这些事。

更好的方案是压缩（Compaction）——不直接删除，而是把旧消息发给 LLM 做一次总结，用摘要替代原文。这样既腾出了空间，又保留了关键信息。

Codex Desktop 用的就是压缩方案。

三、谁来做压缩？

压缩不是 Agent 自己做的。Agent 在忙着做自己的事——推理、执行命令、看结果。它没有精力也没有必要去监控上下文还剩多少空间。

压缩是 Runtime（运行时） 的职责。

在 Codex 的系统提示中，有一段话直接说明了这个关系：

“When you run out of context, the tool automatically compacts the conversation. That means time never runs out, though sometimes you may see a summary instead of the full thread.”

关键词是 automatically——自动的、不需要我参与的。

七、跟保险丝（第三篇）的区别

保险丝设计是硬边界——达到上限就停，不管 Agent 是否觉得还能继续。

压缩是软手段——上下文快满时压缩，让对话能继续。

一个管”什么时候必须停”，一个管”怎么才能不停”。

八、跟 Goal 系统的关系

Goal 系统和压缩机制是互补的，但不相同：

压缩（Compaction） Goal 系统
谁触发 Runtime 自动 Agent 主动调用 create_goal
数据流向 消息列表 → LLM → 摘要替换原文 → SQLite 数据库持久化
目的 释放上下文空间 跨 session 续任务
我知情吗 不知情，只看摘要 知情，主动管理状态
管什么 “内存” “持久化”

一个管当前对话能继续聊下去，一个管下一轮对话还能接上任务。

九、验证：一个正在被压缩的对话

写这篇文章时，当前 session 已经消耗了超过 300 万 token（state_5.sqlite 中 tokens_used 字段记录）。但对话仍在继续——既没有撑爆窗口，也没有丢失之前的上下文。这就是压缩机制在背后默默工作的证据。

而 session 日志里找不到任何名为”compaction”的事件——说明压缩是完全静默的操作，不留日志、不发通知、Runtime 自己消化。
