什么是 Reactor 模型：监控 + 通知 + 异步

发表于 2026-08-16 更新于 2026-08-20 分类于 网络编程 本文字数： 920 阅读时长 ≈ 3 分钟
用餐厅点餐的类比，把 Reactor 模型拆成三个关键词——监控、通知、异步，并讲清楚"会不会阻塞"这个核心判断标准。

这篇文章不是从源码出发，而是从一个问题出发：当几万个客户端同时连着一台服务器，它凭什么只用少量线程就扛得住？

一、先从线程数量说起

直觉上，服务器处理 N 个客户端，最笨的办法是给每个客户端开一个线程。但客户端一多就撑不住了——线程是稀缺资源，光切换上下文就能把 CPU 耗光。

所以 Reactor 模型的第一件事是：让 N 个客户端共用少数几个线程。监控线程负责”看”，公用线程负责”干”。

二、一个餐厅的类比

你在餐厅点菜，菜要等很久。你不会站在厨房窗口盯着厨师炒菜——你会回座位玩手机、聊天。

  • 厨房 = 数据库（真正慢的地方）
  • 前台/监控 = reactor 线程
  • 你 = worker 线程

菜做好之后，你怎么知道可以取餐了？靠厨房主动通知（喊号、亮屏），而不是你隔几秒跑去问一次。

这就是 Reactor 模型的三个关键词之一：异步通知——外部干完了主动喊你，而不是反复去问。

三、三个关键词

Reactor 模型可以浓缩成一句话：监控 + 通知 + 异步。

  1. 监控：一个专门的 reactor 线程盯着所有客户端连接，看见谁发消息了。这是”通知”的前提——你得先”看见”，才知道该通知谁。
  2. 通知/分派：reactor 线程自己绝不干重活，它把活儿分派给 worker 线程池，然后立刻回到岗位继续盯连接。
  3. 异步：worker 接到慢活儿（比如数据库查询），把查询提交给数据库，自己不蹲在数据库旁边等，而是跳回去处理其他客户端的消息。等数据库查完了，主动通知回来，worker 再回来收尾、回复客户端。

五、最容易想错的地方：怎么判断”快/慢”？

一个很自然的想法是：监控线程按”任务快不快”来决定要不要惊动 worker 池。但时间根本没法提前预测——你无法在消息到达的那一刻知道它要花多久。

真实的判断标准是看这个操作会不会阻塞：

  • 会阻塞（查数据库、读磁盘、请求外部服务……要等外部结果）→ 交给 worker，异步跳着处理
  • 不会阻塞（读内存缓存、纯计算……不需要等任何外部东西）→ reactor 线程自己顺手就做完了，根本不用惊动 worker 池

六、收益

少量线程就能服务大量连接——因为线程不再被”等待”占住。这就是 Reactor 模型存在的意义。

七、补充：这只是最经典的”单 Reactor + worker 线程池”

本文讲的是 Reactor 的经典结构：一个 reactor 线程负责监控和分派，worker 线程池负责干活。

真实的 Netty 用的是它的进阶版——主从 reactor（boss + worker）：boss 线程专门负责接受新连接，接进来之后再交给 worker 组去处理 I/O。相当于多了一层”分派的分派”。这个我们下一篇再展开。
