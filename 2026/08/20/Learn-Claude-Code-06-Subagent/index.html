Learn Claude Code 06：Subagent——用独立上下文拆解复杂任务

发表于 2026-08-20 分类于 Learn Claude Code 本文字数： 2.6k 阅读时长 ≈ 9 分钟
从上下文污染出发，拆解父子 Agent 的委派协议、独立消息历史、结果压缩、工具限制、权限冒泡与共享工作区风险。

系列定位： TodoWrite 让主 Agent 看清任务结构，但所有调查、读取和试错仍然堆在同一份消息历史里。本文增加一个 task 工具，把边界清晰的子任务委派给拥有独立上下文的 Subagent，主线程只接收最终结论。

一、为什么有了计划还需要 Subagent

假设主任务是“修复登录偶发失败并补充测试”。为了定位原因，Agent 可能要：

  • 搜索认证入口；
  • 阅读 Token、缓存和数据库代码；
  • 追踪几十个调用点；
  • 比较测试与生产配置；
  • 查看日志中的失败模式。

这些调查过程会产生大量暂时有用、最终却不重要的信息。即使 TODO 列表始终正确，主上下文也可能被几十次文件读取和搜索结果占满。

Subagent 的思路类似开发者“开一个新终端做专项调查”：

子 Agent 结束后，中间消息历史可以释放，只有高信息密度的结果回到主线程。这是一种上下文隔离与压缩机制，并不只是“多开一个模型”。

四、委派描述就是父子 Agent 的接口契约

如果主 Agent 只传一句“看看认证模块”，子 Agent 很难知道调查边界和期望输出。高质量委派应像一个小型任务说明，至少包含：

  • 目标： 最终要回答什么问题；
  • 范围： 可以检查哪些目录、模块或数据；
  • 约束： 只读还是允许修改，不能做什么；
  • 交付物： 需要结论、文件位置、验证结果还是补丁；
  • 完成标准： 什么证据足以结束。

六、子 Agent 应拥有哪些工具

最小实现通常不给子 Agent task 工具，防止无限递归委派：

工具集合应遵循最小能力原则。只负责代码搜索的子 Agent 甚至只需要 read_file 和 glob；允许写文件会扩大权限面，也会制造并发冲突。

递归深度限制也不能只靠 Prompt 中的“不要再委派”。生产系统应从工具注册层移除委派能力，或由运行框架维护 depth 并拒绝超过上限的创建请求。

同样，每个子 Agent 都需要独立预算：

  • 最大轮数；
  • 最大 Token 或费用；
  • 总运行时间；
  • 工具输出上限；
  • 可取消的子级控制器。

父任务被用户取消时，取消信号应向下传播到所有子 Agent，避免主线程已经停止，后台仍在继续修改文件或消耗额度。

七、上下文隔离不等于权限隔离

子 Agent 拥有新的消息历史，不代表它可以绕过父 Agent 的安全策略。它的每次工具调用仍应经过参数验证、PreToolUse Hooks 和权限管线。

当子 Agent 触发需要人工确认的操作时，常见做法是“权限冒泡”：

不能因为子 Agent 没有自己的交互界面就默认允许，也不应不加说明地静默拒绝。审批请求应带上子任务身份、工具参数和原因，让用户知道究竟是谁要做什么。

八、消息隔离了，文件系统却可能共享

教学版父子 Agent 使用同一个工作目录。于是出现一个重要区别：

子 Agent 修改的文件会立即被父 Agent 看见。这对同步委派很方便，却在并发场景中带来风险：

  • 两个子 Agent 同时编辑同一文件，后写覆盖先写；
  • 父 Agent 基于旧内容生成补丁，覆盖子 Agent 的新修改；
  • 子 Agent 修改了工作区，却只在摘要中报告部分变化；
  • 一个子任务失败，留下半完成状态影响后续任务。

因此，同步子 Agent 最好一次只负责边界清楚的修改；多个写任务并行时，应分配不相交的文件范围，或使用独立 Worktree、事务式补丁和合并阶段。共享工作区是一种协作机制，也是一种共享可变状态。

九、同步、异步与 Fork 是不同问题

最容易理解的是同步子 Agent：父 Agent 调用 task 后等待，收到结果再继续。除此之外还有两种常见演进：

模式 父 Agent 行为 适合场景
同步 等待子任务完成 后续步骤依赖子任务结果
异步 立即继续，稍后接收通知 相互独立、耗时较长的调查
Fork 上下文 继承可复用的父消息前缀 子任务高度依赖父上下文或 Prompt Cache

Fork 并不是完全“干净”的新上下文，它可能保留父线程的消息前缀，以共享必要背景或提高 Prompt Cache 命中率。要想命中缓存，System Prompt、工具定义、模型、消息前缀和思考配置等内容通常需要保持一致。

所以，“子 Agent 一定拥有完全空白上下文”只是教学阶段的简化。真实系统应根据隔离程度、背景复用、延迟与成本选择运行模式。

十、什么时候不该使用 Subagent

委派本身有固定成本：构造任务说明、再次调用模型、重复读取背景、压缩结果、处理失败。如果任务只需要一次文件读取或简单命令，直接执行往往更快。

适合委派的任务通常具有以下特征：

  • 边界清晰，可以写出独立完成标准；
  • 会产生大量中间上下文，但主线程只需要结论；
  • 可以与主任务或其他子任务相对独立地进行；
  • 需要不同的工具、模型、System Prompt 或专业知识。

不适合委派的任务包括：步骤极短、与主线程频繁来回依赖、多人同时修改同一小段代码，或背景难以完整描述的工作。

十一、这一篇真正需要记住什么

  1. Subagent 首先解决上下文污染。 独立消息历史承载探索过程，主线程只保留高密度结论。
  2. 委派描述是接口契约。 目标、范围、约束、交付物和完成标准都应明确。
  3. 结果要压缩，但不能丢失证据。 结论之外还应报告产物、风险和验证状态。
  4. 工具与预算必须受限。 禁止无界递归，限制轮次、时间、Token，并传播取消信号。
  5. 权限不会因上下文隔离而消失。 子调用仍走同一安全管线，需要审批时向父界面冒泡。
  6. 共享工作区仍是共享状态。 并行写入需要文件边界、Worktree 或明确的合并机制。

有了 Subagent，主 Agent 能把不同问题交给独立上下文，但子任务所需的专业知识仍然可能让 System Prompt 越来越大。下一篇将进入 Skills：只在任务需要时加载对应知识，而不是把所有说明一次性塞给每个 Agent。
