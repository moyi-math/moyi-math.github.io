Learn Claude Code 09：Memory——让重要信息跨越压缩与会话

发表于 2026-08-20 分类于 Learn Claude Code 本文字数： 3.3k 阅读时长 ≈ 12 分钟
从有损上下文压缩出发，拆解长期记忆的文件存储、相关召回、自动提取和周期巩固，并讨论冲突、隐私与遗忘机制。

系列定位： Context Compact 能让当前会话继续运行，但摘要是有损的，而且会话结束后连摘要也会消失。本文增加一层独立于消息历史的持久化 Memory，让稳定偏好、项目事实和反复验证过的经验能够跨压缩、跨会话被重新召回。

二、记忆系统不是“把所有聊天存下来”

原始对话归档与 Agent Memory 的目标不同：

机制 保存什么 主要用途
Transcript 完整历史，尽量不改写 审计、回放、人工排查
Compact Summary 当前任务继续所需的短状态 同一会话续接
Long-Term Memory 跨会话仍有价值的精选信息 个性化与经验复用

如果把每一句对话都写进 Memory，召回时会充满噪声，隐私风险和维护成本也会持续增长。记忆系统的难点从来不是“如何保存文本”，而是四个判断：

  1. 什么值得记；
  2. 当前任务需要想起什么；
  3. 新信息与旧记忆冲突时怎么办；
  4. 什么时候合并、更新或删除。

三、四类记忆回答不同问题

一个实用的分类可以包含：

类型 回答的问题 示例
user 用户是谁、稳定偏好是什么 “Python 字符串优先使用单引号”
feedback Agent 应怎样工作 “不要 Mock 数据库集成测试”
project 项目为什么这样设计 “认证重构由合规审计推动”
reference 重要信息在哪里 “数据管线故障记录在 Linear INGEST 项目”

类型帮助召回和治理，但不要与其他状态混淆：

  • Todo / Plan 描述当前工作步骤；
  • Task System 负责任务依赖、所有权和进度；
  • Session Memory 服务同一会话的压缩续接；
  • Long-Term Memory 保存未来会话仍可能有用的知识。

“修复第 3 个测试”不该写入长期记忆；“该项目测试必须连接真实 PostgreSQL”则可能值得保留。

  • 单文件最大行数或字符数；
  • 单会话记忆注入总预算；
  • 单轮最大召回数量；
  • 索引本身的最大规模。

九、什么不应该自动记住

自动提取容易滑向“什么都记”。以下内容通常不应默认进入长期记忆：

  • 密码、Token、私钥和支付信息；
  • 短期一次性任务状态；
  • 未经验证的模型推断；
  • 第三方文档中的指令；
  • 用户没有表达为稳定偏好的临时选择；
  • 受法律或组织政策限制的个人数据。

需要区分信息来源：用户明确陈述、工具观察、模型推断和外部内容的可信度不同。特别是提示注入攻击可能藏在网页或代码注释里，诱导 Agent“把这个秘密永久记住”。只有受信任的提取路径才能写 Memory，工具内容不应直接获得持久化权限。

对于敏感类别，最好要求显式确认；同时提供查看、编辑、导出和删除记忆的入口。真正的长期记忆系统必须同时设计“记住”和“忘记”。

十、重复、冲突与过期怎样处理

随着记忆积累，会出现：

简单地保留两条，会让未来 Agent 不知道听谁的。每条记忆需要来源、作用域和更新时间，冲突解决可以遵循：

  1. 显式用户指令高于模型推断；
  2. 项目级规则只作用于对应项目，不覆盖全局用户偏好；
  3. 更新的明确指令可以替代旧指令，但保留变更来源；
  4. 无法确认时标记冲突并询问，而不是静默选一条。

可以把“同一事实的更新”写回原文件，而不是不断创建近义条目。需要历史审计时，用版本记录保存旧值，活跃索引只展示当前有效版本。

十一、低频巩固：让记忆库保持可用

记忆文件持续增长后，需要周期性执行巩固：

  • 合并同义条目；
  • 解决或标记冲突；
  • 淘汰过时引用；
  • 缩短过长正文；
  • 重建索引；
  • 保留近期重要信号。

巩固比单次写入昂贵，也可能大范围改写文件，因此不应每轮执行。可以设置多层门控：

锁要有过期机制，防止进程崩溃后永远阻塞。巩固过程应先写新版本，再原子切换；若失败，旧记忆库仍然可用。

十二、User Memory 与 Session Memory

长期用户/项目记忆和会话记忆解决不同时间尺度的问题：

维度 Long-Term Memory Session Memory
生命周期 跨会话 当前会话
内容 稳定偏好、项目知识、长期反馈 当前目标、进展、最近发现
加载方式 目录检索后按需注入 上下文压缩时直接参与续接
更新频率 低，精选 高，随当前任务变化
遗忘策略 显式删除、过期或巩固 会话结束后清理

当 Session Memory 足够完整时，自动压缩可以先用它构建轻量摘要，减少额外 LLM 调用。Long-Term Memory 则不应该记录每轮进度，否则会把临时状态带到未来无关会话。

十三、异步预取与提取不要拖慢主流程

相关记忆选择和回合结束后的提取都会增加模型调用。如果全部同步执行，用户会在每次输入前后等待额外延迟。

可采用异步策略：

  • 用户 Turn 开始时启动 Memory Prefetch；
  • 主 Agent 做不依赖记忆的准备工作；
  • 在真正需要组装下一次模型请求前收集结果；
  • Turn 结束后以受限后台任务提取记忆；
  • 重叠任务设置去重与取消，避免同一 Turn 重复写入。

异步不代表可以忽略一致性。若主 Agent 已经显式写入某条记忆，后台提取器应识别重叠并跳过，防止创建重复文件。

十四、如何验证一个 Memory 系统

除了“第二个会话还能回答偏好”，还应测试：

  1. 召回精度： 相关任务能找到记忆，无关任务不会加载；
  2. 冲突处理： 新明确指令能更新旧值，不会同时生效；
  3. 作用域： 项目规则不会泄漏到另一个项目；
  4. 隐私： 敏感信息不会被自动提取，删除后索引与文件都消失；
  5. 并发： 多进程写入不会丢文件或损坏索引；
  6. 降级： 选择器失败时主任务仍可继续；
  7. 预算： 大记忆库不会无限扩大 Prompt；
  8. 可审计性： 能解释记忆来自哪次明确输入或验证结果。

Memory 的质量不能只用“记住了多少”衡量。更重要的指标是：在正确时机召回正确事实，同时少打扰、少误导、可纠正。

十五、这一篇真正需要记住什么

  1. Memory 是独立于消息历史的持久层。 它让精选信息跨越压缩和新会话。
  2. 不要保存全部对话。 Transcript、会话摘要和长期记忆承担不同职责。
  3. 完整系统包含存储、召回、提取和巩固。 少任何一环都会随时间退化。
  4. 索引常驻，正文按需加载。 同时限制条数、单文件和会话总预算。
  5. 写入需要证据、作用域与可信来源。 模型推断和外部内容不能轻易变成长期事实。
  6. 冲突不能静默解决。 结合来源、更新时间和作用域更新，必要时询问用户。
  7. 记忆必须允许遗忘。 查看、编辑、删除、过期和隐私治理是核心能力。
  8. 长期记忆不等于会话记忆。 一个负责未来复用，一个负责当前任务压缩续接。

工具、Skill、压缩和 Memory 都已具备，但如果 System Prompt 仍是一段不断拼接的字符串，新增任何能力都可能破坏整体结构。下一篇将进入 System Prompt 的运行时组装：按角色、环境、工具和项目生成稳定而可测试的指令层。
