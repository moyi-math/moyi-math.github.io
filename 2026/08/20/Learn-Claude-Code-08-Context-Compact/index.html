Learn Claude Code 08：Context Compact——给长期运行的 Agent 腾出空间

发表于 2026-08-20 分类于 Learn Claude Code 本文字数： 3.1k 阅读时长 ≈ 11 分钟
从上下文窗口耗尽出发，拆解工具结果预算、历史裁剪、微压缩、语义摘要与应急恢复组成的分层压缩管线。

系列定位： Agent 已经能加载 Skill、调用工具、维护计划和委派子任务，但所有请求、响应与工具结果仍不断追加到 messages。上下文窗口有限，长期运行最终一定会撞上边界。本文设计一条从便宜到昂贵的压缩管线，在尽量少丢信息的前提下延长会话寿命。

一、上下文窗口为什么总会被填满

Agent 的每轮循环都会增加消息：

文件内容、测试日志和搜索结果往往比自然语言回答大得多。读取一个千行文件可能消耗数千 Token，一条递归构建日志也可能占据数百 KB。随着工具调用累积，即使模型能力和剩余任务都没有问题，API 也可能因为输入超过窗口而拒绝请求。

上下文管理因此不是“有空再优化”的性能功能，而是长任务能否继续执行的生存机制。

二、压缩真正优化的不是消息条数

只限制 messages 数量并不可靠：50 条短消息可能很小，一条大工具结果却可能填满整个窗口。压缩系统至少要同时观察：

  • 输入 Token 估算；
  • 单条工具结果大小；
  • 当前轮所有工具结果总量；
  • 历史工具结果的年龄和可重建性；
  • System Prompt、工具 Schema 与预留输出空间。

可用输入预算不是模型标称窗口本身：

如果压缩阈值等到窗口 100% 才触发，模型连生成摘要的空间都没有。生产系统必须提前预留输出和恢复缓冲。

三、分层原则：便宜、确定的操作先执行

一次完整的 LLM 摘要能大幅缩小历史，却有额外延迟、费用和信息失真风险。更合理的策略是先运行不需要模型的确定性预处理器：

这里的层级按实际执行顺序描述。核心原则是：先处理体积异常，再清理确定冗余，最后才花一次模型调用理解和总结历史。

四、L1：为当前轮工具结果设置预算

单次响应可能同时读取多个大文件。如果先把旧结果替换成占位符，完整内容可能尚未来得及持久化就丢失。因此第一步应处理当前轮的大输出。

需要保留三类信息：

  1. 完整结果保存在哪里；
  2. 足以判断内容类型的短预览；
  3. 清晰标记当前内容已被截断。

落盘目录不能位于可公开发布或被 Git 默认提交的位置；文件名应由运行框架生成，避免使用不可信的工具输入。输出中可能包含源码、凭证和用户数据，因此还需要访问控制、生命周期清理和加密策略。

五、L2：裁剪历史时不能破坏消息协议

当消息数量持续增加，可以保留早期任务入口和最近工作区间，裁掉中间的旧探索：

但切口不能随意落在两个数组下标之间。工具调用是一组协议单元：

如果只保留后一条，会出现孤立的 tool_result；如果只保留前一条，则模型看到一个永远没有结果的调用。很多 API 会直接拒绝这种无效消息结构。

因此，裁剪算法应以“消息组”而不是单条消息为单位，至少保证：

  • tool_use 与对应 tool_result 同时保留或同时移除；
  • 多工具调用的一组结果不能只留下部分；
  • 角色顺序仍满足 API 协议；
  • 切口处插入明确的压缩边界消息。

六、L3：用占位符替换过时工具结果

即使消息条数不多，旧 tool_result 仍可能占据大量空间。可保留最近若干结果全文，把更老的大结果替换为可恢复占位符：

这种方法便宜，但会牺牲 Prompt Cache 命中，也可能让模型重复读取文件。生产系统可以维护 readFileState：记录文件路径、内容版本或哈希；压缩后若文件未变化，返回简短的“内容未变化”标记，并按预算恢复最近读取的关键文件。

并非所有工具结果都适合清空。用户审批、不可逆操作的确认、生成的唯一标识和无法重放的外部响应，可能比普通文件读取更需要保留。压缩策略应按工具类型和结果语义分级，而不只是看位置。

七、L4：用 LLM 把历史压成可继续工作的状态

前三层只理解结构和大小，不理解任务语义。当 Token 仍超过阈值时，需要让模型生成一次交接摘要。

摘要不是普通“聊天总结”，而是新上下文的启动状态，至少应保留：

  • 用户当前目标与成功标准；
  • 不可违反的约束和用户偏好；
  • 已完成工作及验证证据；
  • 修改过的文件和关键代码位置；
  • 重要发现、失败尝试与原因；
  • 当前 TODO 状态与下一步；
  • 已加载的 Skills、关键规则和版本；
  • 权限拒绝、未解决风险与开放问题。

压缩前先保存完整 Transcript：

摘要调用必须禁止使用工具。否则模型可能在“整理历史”的特殊调用中继续修改文件，产生主循环无法正确关联的副作用。可以使用不提供 Tools 的独立请求，并对返回格式进行校验。

Transcript 保证审计与人工恢复，不代表模型仍然“记得”其中内容。除非提供检索工具，退出活跃上下文的细节对模型来说就是不可访问的。

八、压缩后不能只剩一段孤立摘要

最小实现可以用一条摘要替换全部历史，但生产 Agent 往往需要重新挂载运行状态：

这叫“后压缩恢复”。如果摘要说“继续修改 auth.py”，但关键函数内容已被压掉，模型只能重新读文件；适度恢复最近文件可以减少一次往返，但也必须受总 Token、文件数和单文件额度限制。

恢复顺序还要尊重新鲜度：文件在摘要生成后可能已经被其他 Agent 修改，不能盲目附加旧缓存。应校验哈希或修改时间，发现变化就重新读取。

九、主动压缩、自动压缩与响应式压缩

压缩可以由三类信号触发：

模式 触发条件 特点
主动 用户或模型调用 compact 可在自然阶段边界整理上下文
自动 估算 Token 超过预警阈值 常规防护，留有摘要生成空间
响应式 API 返回 prompt_too_long 应急恢复，通常更激进

响应式压缩处理的是“预估失败”或“上下文突然增长”。它可以生成摘要后保留最近的一小组完整消息，再重试原请求。但必须设置严格上限：

如果摘要连续失败还无限重试，只会重复消耗费用。自动压缩也需要失败计数和熔断器，达到上限后向上层报告明确错误。

十、为什么处理顺序不能随便换

一条稳妥的预处理顺序是：

先处理工具结果预算，是为了在完整大输出仍然存在时将其持久化；若先执行微压缩，原内容已经被占位符覆盖，就没有完整结果可保存。

先确定性压缩、后语义摘要，也让摘要模型看到更少噪声，降低费用。压缩层之间不是互相替代，而是按成本和信息损失逐级升级。

十一、压缩的质量怎样验证

“Token 下降了”只说明压缩变小，不说明 Agent 还能继续正确工作。可以从四个维度验证：

  1. 结构有效性： 消息角色与工具调用配对是否仍符合 API 协议；
  2. 任务连续性： 压缩后能否准确说出目标、当前步骤和剩余工作；
  3. 事实保持： 文件修改、测试结果和用户约束有没有被摘要扭曲；
  4. 恢复能力： 被移除的细节能否通过 Transcript 或重新调用工具找回。

适合建立回归用例：给定固定的长历史，执行压缩后断言关键约束仍存在、敏感内容未意外扩散、所有 tool_result 都有对应调用，并让 Agent继续完成一个后续步骤。

十二、压缩不是记忆

Context Compact 的目标是让当前会话继续运行。它会主动舍弃细节，只保留对眼前任务最有价值的信息。

Memory 解决的是另一个问题：哪些偏好、事实和经验值得跨压缩甚至跨会话保留。两者可以这样区分：

如果把所有历史都写进长期记忆，噪声和隐私风险会迅速累积；如果只依赖压缩摘要，用户偏好又可能随着多次压缩逐渐失真。下一篇的 Memory 将处理选择、提取与巩固。

十三、这一篇真正需要记住什么

  1. 上下文一定会满，压缩必须是运行框架能力。 不能等 API 拒绝后才临时补救。
  2. 按实际 Token 和输出体积管理预算。 消息条数只是粗略信号。
  3. 先便宜后昂贵。 大结果持久化、历史裁剪和微压缩先运行，最后才调用 LLM 摘要。
  4. 工具调用配对是硬约束。 裁剪不能制造孤立的 tool_use 或 tool_result。
  5. 摘要必须面向继续工作。 保留目标、约束、证据、文件、计划、风险和下一步。
  6. 压缩后要恢复必要运行状态。 最近文件、计划与 Skill 约束应按预算重新挂载。
  7. 所有压缩路径都要有限重试。 自动和响应式压缩需要熔断，避免费用死循环。
  8. Transcript 是敏感资产。 它需要访问控制和清理策略，也不等同于模型可访问记忆。
