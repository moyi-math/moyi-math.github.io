PostgreSQL 的“离谱”设计：多进程、双重缓存与 Direct I/O

发表于 2026-08-20 分类于 PostgreSQL 原理 本文字数： 3.9k 阅读时长 ≈ 14 分钟
从每连接一进程、shared_buffers 与 OS Page Cache、Direct I/O 三条路径，拆解 PostgreSQL 的历史设计究竟贵在哪里、什么时候会成为问题，以及 PostgreSQL 18 的 AIO 改变了什么。

一条连接为什么要配一个进程？同一数据页为什么可能缓存两次？PostgreSQL 18 有了 AIO，是否就等于解决了 Direct I/O？

围绕 PostgreSQL 的架构取舍，常见三个很有冲击力的观点：每连接一进程模型太重，shared_buffers 与操作系统页缓存会形成双重缓存，MVCC 还带来了 VACUUM、表膨胀和 XID 回绕等维护成本。

这些现象大体存在，但“存在成本”和“设计错误”不是一回事。本文不复述视频的情绪化结论，而是把问题拆成可验证的机制：成本从哪里产生，什么场景会放大它，哪些反例能限制结论，以及今天的 PostgreSQL 已经演进到哪里。

本文涉及版本变化的部分以 PostgreSQL 18 文档为准，核对时间为 2026 年 8 月。

一、先说结论

  1. PostgreSQL 当前仍采用每条客户端连接对应一个 backend 进程的模型。大量直连、连接频繁创建或并发突然升高时，进程私有内存、初始化和调度成本会被放大。
  2. fork() 不会把整个数据库缓存复制一份。shared_buffers 本来就是共享内存，普通内存也有 Copy-on-Write；真正需要关注的是进程元数据、页表、私有会话内存和高并发调度。
  3. PostgreSQL 默认的缓冲 I/O 可能让同一数据页同时存在于 shared_buffers 与 OS Page Cache。它会造成内存重叠，但 OS 缓存也提供预读、回写和二次命中的价值，不能把两层缓存全部视为浪费。
  4. PostgreSQL 18 引入了新的异步 I/O（Asynchronous I/O, AIO）子系统，但 AIO 与 Direct I/O 是两个不同维度。当前 debug_io_direct 仍是开发测试选项，官方明确说明它可能降低性能。
  5. 多进程、双重缓存和 MVCC 维护成本是三组不同问题。把它们都归结为“PostgreSQL 架构落后”，无法指导实际调优。

下面逐个展开。

二、每条连接一个进程，具体贵在哪里

PostgreSQL 的主进程监听连接。客户端接入后，服务器创建一个新的 backend 进程；从解析 SQL、生成执行计划到执行和返回结果，都由这个 backend 代表该会话完成。

这个模型最容易在“连接数远大于同时执行的查询数”时暴露成本。

1. 例子：一万个连接，只有五十个正在查询

假设一台 32 核数据库服务器面对 10,000 个应用连接，但任意时刻通常只有 50 个连接在执行 SQL，其余都处于 idle。

2. 成本一：连接创建与销毁

如果应用没有连接池，每个请求都这样访问数据库：

对于只需几毫秒甚至更短的简单查询，TCP、TLS、认证、进程创建和会话初始化可能占据显著比例。连接越短命，这部分固定成本越不划算。

这也是为什么“数据库能执行多少条简单 SQL”与“数据库能建立多少条新连接”必须分开测试。前者测执行路径，后者还测连接生命周期。

3. 成本二：私有内存，而不是复制整个 shared_buffers

Linux 的 fork() 使用 Copy-on-Write，不会在创建进程时立刻复制所有物理页。PostgreSQL 的 shared_buffers、WAL 缓冲区、锁表等本来就是多个进程共同映射的共享内存。

但每个 backend 仍有自己的：

  • 进程描述符、页表、栈和文件描述符；
  • 会话状态与内存上下文；
  • 查询解析、规划和执行期间申请的私有内存；
  • 排序、哈希、聚合等算子受 work_mem 影响的内存。

因此，不能拿 top 中某个 backend 的 RSS 直接乘以连接数——RSS 会把共享映射重复计算。更合理的方式是观察 private memory 或 PSS。假设实测每个空闲 backend 平均产生 3 MB 私有内存，那么：

4. 成本三：突发并发与上下文切换

空闲 backend 在睡眠时不会持续消耗 CPU。问题发生在大量进程同时被唤醒时：

固定工作池可以只放 64 个任务执行，其余排队，从而主动限制并发。PostgreSQL 的原生模型则更依赖应用连接池、max_connections 和外部连接池控制入口。

这里也有两个边界：

  • Linux 把进程和线程都作为调度任务处理，二者的切换成本并非数量级差异；
  • 如果 1,000 条查询都是真正的 CPU 重活，换成线程也不会让计算量消失。工作池的价值是控制拥塞，而不是创造算力。

5. 成本四：跨进程共享状态

两个 backend 同时修改一张表时，必须共同访问：

  • shared_buffers 中的数据页；
  • WAL 缓冲区；
  • 锁表和活跃事务数组；
  • 各类共享统计与控制结构。

独立进程不能随意共享普通堆指针，因此 PostgreSQL 需要预先设计共享内存布局，并通过信号量、轻量锁、latch 和信号等机制同步。这提高了内部实现复杂度。

不过线程模型也必须为数据页、锁表和事务状态做并发控制。线程的共享更直接，但一次越界写或内存破坏也更容易拖垮整个服务进程；多进程则提供了更清晰的地址空间和故障边界。

6. 工程上如何处理

如果业务有大量客户端连接，不要让它们全部直接变成 PostgreSQL backend：

连接池不能无限开大。一个常见事故是：20 个微服务实例，每个实例默认开 50 个连接，最终数据库突然收到 1,000 个 backend；扩容应用反而把数据库压垮。

真正需要先回答的是：业务需要多少并发查询，而不是能创建多少连接。

1. 一个 128 GB 内存的例子

假设专用数据库服务器有 128 GB 内存：

如果把 shared_buffers 直接设成 100 GB，留给操作系统、连接私有内存、排序哈希和后台任务的空间会明显收紧。查询并发升高时，剩余内存可能不足，最终触发 swap 或 OOM，代价远大于多缓存一点数据。

PostgreSQL 18 官方文档仍把系统内存的 25% 作为专用数据库服务器的合理起点，并指出由于 PostgreSQL 依赖操作系统缓存，超过约 40% 往往未必更好。这是起点，不是适用于所有负载的定律。

2. 两层缓存不全是浪费

如果同一热页长期同时占据两层缓存，确实会降低有效缓存容量。但 OS Page Cache 也不是毫无价值：

  • PostgreSQL 刚从 shared_buffers 淘汰的页面，可能仍在 OS 缓存中，再次读取时不必访问磁盘；
  • 内核提供文件预读、脏页回写和统一的内存回收；
  • PostgreSQL 无需为所有文件系统和设备重新实现一套完整缓存管理。

因此，问题不是“为什么不把 OS Page Cache 全关掉”，而是：数据库是否能比通用内核更准确地管理自己的访问模式，以及为这种控制权要付出多少复杂度。

3. 与 InnoDB 的对比

MySQL/InnoDB 在常见 Unix-like 配置中可以使用 O_DIRECT：

这样数据文件 I/O 可以绕过 OS Page Cache，把主要缓存决策交给 Buffer Pool，减少同一数据页在两层缓存中的重叠。

但这并不意味着 O_DIRECT 在所有设备和负载上都更快。对齐要求、I/O 合并、预读、队列深度和存储设备特征都会影响结果；InnoDB 的实际路径也取决于平台与配置。比较两个数据库时，不能把“MySQL”简单等同于“永远绕过页缓存”。

四、Direct I/O 与 AIO 不是一回事

这两个概念经常被混在一起：

概念 回答的问题 典型作用
Direct I/O 数据是否绕过 OS Page Cache 减少双重缓存，让数据库掌控缓存
AIO 发出 I/O 后是否必须原地等待 同时排队多个请求，提高设备并行度

可以有缓冲式 AIO，也可以有 Direct I/O 加 AIO。一个解决缓存路径，一个解决等待和并发提交。

1. 视频中的 PostgreSQL 16 状态

视频提到 PostgreSQL 16 的 debug_io_direct = data。这个参数能够让内核尽量减少对关系数据或 WAL 的缓存，但它位于 Developer Options，官方说明它需要特定调试构建，并且当前会降低性能，只用于开发测试。

2. PostgreSQL 18 新增的是 AIO 子系统

PostgreSQL 18 引入了核心 AIO 基础设施，可以让 backend 同时排队多个读取请求。顺序扫描、位图堆扫描和 VACUUM 等路径可以从中受益。

3. 为什么一个 +5.8% 的实验不能证明结论

视频引用过一项历史实验：补丁尝试在数据进入 shared_buffers 后，通过 posix_fadvise(POSIX_FADV_DONTNEED) 释放 OS 中的重复缓存；某组 DBT-2 结果从 3589 提升到 3799，约为 5.8%。

这个结果适合作为“重复缓存可能存在成本”的证据，但不能直接推出“生产环境都能提升 5.8%”：

  • 它来自特定硬件、内核、数据规模和 DBT-2 负载；
  • 丢弃页缓存可能破坏内核预读，或误删仍然有价值的热页；
  • posix_fadvise 是提示，不同内核和文件系统实现可能不同；
  • 补丁作者也提醒提升可能落在误差范围，方案最终没有成为通用默认路径。

基准测试回答的是“在这组条件下发生了什么”，不是“所有环境下必然发生什么”。

五、VACUUM、表膨胀和 XID 回绕是另一组问题

视频最后提到 PostgreSQL MVCC 的三类维护成本：

  1. UPDATE 和 DELETE 产生的旧行版本不会立即物理删除，需要 VACUUM 回收；
  2. 旧版本和索引项清理不及时，会产生表或索引膨胀；
  3. 事务 ID 是有限空间，需要 freeze 机制避免 XID 回绕风险。

这些问题真实存在，但它们不是多进程或双重缓存直接导致的。它们来自 PostgreSQL 的 MVCC 元组版本与可见性设计。

因此，评估时应拆成三张账：

问题 主要观察对象
连接进程过多 backend 数、连接建立速率、PSS、CPU 调度
缓存与 I/O shared_buffers 命中、OS 缓存、pg_stat_io、存储延迟
MVCC 维护 dead tuples、autovacuum、表/索引膨胀、freeze 年龄

把三类指标混在一起，只会得到“数据库好像很慢”，却不知道该减少连接、调整缓存，还是修复 autovacuum。

六、如何判断自己的系统是否真的受影响

1. 先看连接，而不是先改参数

如果大量连接长期 idle，先检查应用连接池和连接池总量。如果 backend 数量并不高，多进程模型通常不是当前瓶颈。

2. 不要用 RSS 粗暴相乘

七、重新评价这些“离谱设计”

PostgreSQL 的多进程模型来自历史，但今天仍有清晰的工程收益：地址空间隔离、故障边界、扩展模型和长期兼容性。代价是在海量连接和突发并发下，需要更严格地控制 backend 数量。

shared_buffers 与 OS Page Cache 的双重缓存可能浪费内存，但也借用了成熟的内核预读、回写和缓存回收。Direct I/O 能获得更多控制权，同时也把对齐、队列和缓存策略的复杂度交还给数据库。

所以更准确的结论不是“PostgreSQL 设计落后”，而是：

PostgreSQL 选择了隔离性、通用性和长期兼容；当连接规模、内存压力或 I/O 模式越过边界时，这些选择的成本就会显现。工程任务不是站队，而是找到边界并用指标验证。
